# HTTP request smuggling (рассинхронизация фронт/бэк)

## Суть
Между клиентом и приложением обычно стоит цепочка: CDN → nginx/Caddy → uvicorn.
Если два звена по-разному решают, где кончается один запрос и начинается
следующий, хвост одного запроса «приклеивается» к началу чужого на общем
keep-alive-соединении. Итог — обход проверок на фронте, кража чужих запросов
(с куками), отдача одному пользователю ответа другого, отравление кэша.
Это почти всегда ошибка конфигурации и стыка компонентов, а не бизнес-кода.

## Где появляется в коде
- Конфиги прокси: `proxy_pass` к бэкенду по HTTP/1.1 с keep-alive
  (`proxy_http_version 1.1` + `keepalive` в `upstream`), HTTP/2 снаружи и
  даунгрейд в HTTP/1.1 к бэку (обычная схема nginx/Caddy/ALB → uvicorn).
- Старые/самописные прокси и балансировщики, свой «шлюз» на Python, который
  читает сокет и пересылает байты, сам разбирая `Content-Length`.
- ASGI/WSGI-сервер без строгого парсера (устаревшие версии uvicorn/h11/gunicorn,
  `httptools` старых версий), сервер за нестандартным прокси.
- Код, который сам собирает HTTP/1-запрос строкой (`f"GET {path} HTTP/1.1\r\n..."`)
  или прокидывает пользовательские значения в заголовки исходящего запроса без
  проверки на `\r`/`\n`.
- Эндпоинты, которые не читают тело (редиректы, статика, health-check, 404),
  если сервер при этом не закрывает соединение — почва для варианта «CL.0».

Плохо (самописный прокси):
```python
headers = {k: v for k, v in request.headers.items()}      # пробрасываем всё как есть
body = await request.body()
raw = f"{request.method} {request.url.path} HTTP/1.1\r\n" + \
      "".join(f"{k}: {v}\r\n" for k, v in headers.items()) + "\r\n"
```
Хорошо: использовать штатный проксирующий сервер или `httpx` (он сам кодирует
запрос), выкидывать hop-by-hop заголовки (`Connection`, `Transfer-Encoding`,
`Content-Length` — пересчитает клиент), отклонять значения с CR/LF.

## Как искать
```
rg -n "proxy_pass|proxy_http_version|keepalive|upstream|reverse_proxy|transport http" deploy/ infra/ *.conf Caddyfile
rg -n "chunked_transfer_encoding|underscores_in_headers|ignore_invalid_headers|merge_slashes"
rg -n "Transfer-Encoding|Content-Length" app/            # ручная работа с длиной
rg -n "HTTP/1\.[01]\\\\r\\\\n|\\\\r\\\\n\\\\r\\\\n" app/  # сборка запроса строкой
rg -n "socket\.|asyncio\.open_connection|StreamReader" app/
```
Что смотреть в конфиге прокси:
- Версии фронта и бэка (nginx, Caddy, HAProxy, uvicorn, h11) — известные CVE
  рассинхронизации закрыты в свежих версиях; устаревший компонент — главный риск.
- Снаружи HTTP/2, к бэку HTTP/1.1? Если да — фронт должен валидировать
  переписанные заголовки (переводы строк, двоеточия в именах, пробелы в методе).
- Переиспользуются ли соединения к бэку (`keepalive` в upstream)? Это включает
  риск смешения запросов разных пользователей.
- Разрешены ли «невалидные» заголовки (`ignore_invalid_headers off`,
  подчёркивания) — расширяет поле для расхождений.
- Пускает ли фронт запросы с одновременно `Content-Length` и `Transfer-Encoding`,
  с несколькими `Content-Length`, с телом в GET/HEAD.
- Есть ли перед nginx ещё один слой (CDN, облачный балансировщик) — расхождение
  может быть между ними, а не с приложением.

Вопросы ревьюера: на фронте есть проверки доступа по пути (например, «/admin
только из VPN»)? Тогда smuggling = их обход, и проверку надо дублировать в
приложении.

## Обходы, о которых забывают
- **Два способа задать длину — два мнения.** В HTTP/1.1 длина тела задаётся либо
  `Content-Length`, либо `chunked`. Если один сервер верит одному, а второй
  другому — граница запроса плывёт. При HTTP/2→HTTP/1 даунгрейде способов
  становится три (собственная длина фреймов HTTP/2 плюс оба заголовка).
- **«Мы отклоняем Transfer-Encoding» недостаточно.** Заголовок можно записать
  так, что один сервер его узнает, а другой — нет (вариации регистра, пробелов,
  дубликаты, нестандартные значения). Тогда «оба понимают TE» сводится к случаю,
  когда понимает только один.
- **HTTP/2 «не подвержен» — только end-to-end.** Как только фронт переписывает
  запрос в HTTP/1, в значения заголовков HTTP/2 можно протащить символы,
  которые после переписывания станут переводами строк.
- **Тело там, где его «не бывает».** Сервер, который предполагает, что у
  какого-то запроса нет тела, и не читает его, оставляет байты в сокете — они
  станут началом следующего запроса (CL.0). Это возможно даже с одним сервером
  и из обычного браузера (client-side desync).
- **Отключить keep-alive к бэку — не панацея.** Это снимает часть атак, но
  туннелирование запроса через фронт к бэку остаётся.
- **Паузы и таймауты.** Если сервер по таймауту отвечает, не дочитав тело, и
  оставляет соединение открытым, недочитанное тело становится новым запросом.
- **Внутренние заголовки фронта.** Фронт добавляет `X-Real-IP`/`X-User` и т.п.;
  контрабандный запрос их не получит или подставит свои — если бэк им верит, это
  обход аутентификации.

## Как исправить правильно
1. Держать фронт и бэк на актуальных версиях; это главная мера.
2. По возможности HTTP/2 до бэка или хотя бы строгая валидация при даунгрейде.
3. Фронт нормализует неоднозначные запросы (оба заголовка длины, дубликаты,
   невалидные символы) — отклоняет их, а не «чинит»; бэк при любой неоднозначности
   возвращает 400 и закрывает соединение.
4. Не предполагать, что у запроса нет тела; сервер должен дочитать или закрыть.
5. При серверной ошибке/таймауте — закрывать соединение.
6. Проверки доступа делать в приложении (`Depends(auth.current_user)`), а не
   только по пути на прокси; не доверять заголовкам, которые «ставит только фронт»,
   если бэк доступен в обход фронта или фронт их не перезаписывает безусловно.
7. Не писать свой HTTP-прокси/парсер; в исходящих запросах отклонять CR/LF в
   значениях заголовков.

## Ложные срабатывания
- Один стандартный прокси (свежий nginx/Caddy) → uvicorn на localhost, без своих
  парсеров: сам факт `proxy_pass` не уязвимость.
- `Content-Length` в коде, который лишь читает его для лимита размера загрузки.
- Ручная сборка заголовков через `httpx`/`requests` словарём — клиент кодирует
  сам и отвергает переводы строк в значениях.
