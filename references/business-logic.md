# Уязвимости бизнес-логики

## Суть
Логическая уязвимость — когда законные функции приложения можно использовать не так,
как задумано: пропустить шаг, подставить неожиданное значение, повторить действие.
Причина — неявные допущения разработчика о том, как «нормальный» пользователь
пройдёт по сценарию. Сканеры такие ошибки почти не находят; последствия — от
мелочей до обхода входа, эскалации прав и прямых денежных потерь.

## Где появляется в коде
- Сервер принимает от клиента то, что должен вычислять сам: цену, сумму, скидку,
  статус, владельца, роль, длительность, номер шага.
- Валидация есть только во фронтенде (`min`, `max`, `required`, disabled-поля).
- Нет проверки диапазона и смысла: отрицательное количество, ноль, огромные числа,
  переполнение, слишком длинные строки, обрезаемые базой.
- Многошаговый процесс без серверного состояния: шаг N не проверяет, что шаги 1…N-1
  пройдены именно этим пользователем и именно для этого объекта.
- Код ветвится по наличию параметра (`if "password" in body`) — отсутствие параметра
  запускает другой путь, часто без проверок.
- Скидка/бонус проверяется при применении, но не пересчитывается после изменения
  корзины/данных.
- Разные компоненты по-разному понимают одно значение (email, домен, путь, регистр).
- Функция, которая шифрует/подписывает пользовательский ввод и возвращает результат
  («оракул»): им можно получить валидный шифротекст для другой функции.

```python
# плохо: доверие клиенту и отсутствие проверки состояния
class Checkout(BaseModel):
    items: list[Item]; total: Decimal; status: str
@app.post("/orders/{oid}/confirm")
async def confirm(oid: int, body: Checkout, user=Depends(current_user)):
    await db.execute("UPDATE orders SET total=$1, status=$2 WHERE id=$3", body.total, body.status, oid)

# хорошо: сумма считается на сервере, переход — по машине состояний, условие в WHERE
@app.post("/orders/{oid}/confirm")
async def confirm(oid: int, user=Depends(current_user)):
    async with db.transaction():
        order = await load_order_for(user, oid, for_update=True)
        if order.status != "paid": raise HTTPException(409)
        total = await compute_total(order.id)          # цены из БД
        await db.execute("UPDATE orders SET status='confirmed', total=$1 "
                         "WHERE id=$2 AND status='paid'", total, oid)
```

```python
# pydantic: смысловые ограничения в схеме
class Item(BaseModel):
    product_id: int
    qty: conint(ge=1, le=100)
```

Node: то же — `zod`/`joi` с `.int().min(1).max(100)`, суммы и статусы только на сервере.

## Как искать
```
rg -n '\b(price|total|amount|discount|balance|status|role|owner_id|step)\b' app/ | rg 'Body|BaseModel|Form|request\.json'
rg -n 'int\b|float\b|Decimal' app/schemas* app/models*     # нет ли ge/le у количественных полей
rg -n 'if .* in (body|data|payload|request)' app/          # ветвление по наличию поля
rg -n 'status\s*=\s*\$|SET status' app/                    # переходы без проверки текущего статуса
rg -n 'coupon|promo|bonus|referral|gift|credit|refund' app/
rg -n 'encrypt\(|sign\(|fernet' app/                       # что подписывается и возвращается клиенту
```
Вопросы ревьюера:
- Какие инварианты у этой функции («сумма заказа = сумма позиций», «один отзыв на
  пользователя», «нельзя принять задачу дважды»)? Где каждый проверяется на сервере?
- Что будет, если прислать значение 0, −1, очень большое, пустое, отсутствующее,
  неожиданного типа?
- Можно ли вызвать шаг 3, минуя 1 и 2? Повторить шаг? Вернуться назад после оплаты?
- После какого изменения данных должна пересчитаться скидка/право/лимит?
- Одинаково ли разные части системы нормализуют email, домен, регистр, юникод?
- Какие значения клиент получает зашифрованными/подписанными и где ещё такие же
  шифротексты принимаются как доверенные?

## Обходы, о которых забывают
- **Клиентские ограничения не существуют для атакующего**: запрос отправляется в
  обход браузера, disabled-поле включается, скрытое меняется.
- **Граничные и «бессмысленные» значения.** Отрицательное количество уменьшает сумму;
  переполнение целого делает сумму отрицательной; длинный email обрезается базой до
  другого домена.
- **Пропущенный параметр.** Удалённое поле `current_password` переключает код на ветку
  «сброс без проверки»; удалённый токен — на ветку «нет токена — значит, первый раз».
- **Пользователь «проверен один раз».** Права, домен, статус проверили при входе или
  на первом шаге, а потом пользователь меняет почту/роль/объект, и проверка не
  повторяется.
- **Порядок шагов.** Финальный шаг принимается без промежуточного; шаг
  повторяется; откат на предыдущий шаг сохраняет выданные бонусы.
- **Скидки и купоны:** применение нескольких в чередовании, применение до изменения
  корзины, возврат товара с сохранением бонуса.
- **Оракул шифрования.** Если одна функция шифрует произвольный ввод (например,
  «запомнить email» в cookie) тем же ключом, что и другая, принимающая
  зашифрованные данные как доверенные, — злоумышленник изготовит нужное значение.
- **Расхождение парсеров email.** Валидатор видит один домен, почтовый сервер —
  другой (кодированные части, кавычки, комментарии); ограничение «только корпоративный
  домен» обходится.
- **Гонки** — отдельный класс, см. `race-conditions.md`.

## Как исправить правильно
- Всё, что влияет на деньги, права, личность и статус, — вычисляется на сервере из
  доверенных данных; от клиента — только намерение (id товара, количество).
- Строгие схемы ввода (pydantic `conint`, `constr`, `Literal`, `extra="forbid"`),
  смысловые проверки диапазонов и сочетаний полей.
- Процессы — серверная машина состояний: переход разрешён только из ожидаемого
  состояния, условие перехода — в `WHERE` (`AND status='paid'`), с проверкой числа
  изменённых строк.
- Повторная проверка условий после любого изменения, от которого они зависят.
- Инварианты — в схеме БД: CHECK (`qty > 0`), уникальные индексы, внешние ключи.
- Нормализация значений одним кодом на всю систему; для email — проверять
  подтверждённый адрес у провайдера, а не строку.
- Разные ключи для разных целей шифрования/подписи; контекст (назначение) внутри
  подписанных данных.
- Лимиты и журнал для функций, раздающих ценность (бонусы, приглашения, промо).
- Документировать допущения и проверять их тестами «нечестного пользователя».

## Ложные срабатывания
- Поле `total` в ответе (не на вход) или во внутренней модели, не принимаемое из запроса.
- Клиентская валидация, которая дублирует серверную, — нормально.
- Админский роут, где изменение статуса вручную — задуманная функция (проверить роль).
