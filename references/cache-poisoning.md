# Web cache poisoning (отравление кэша)

## Суть
Кэш (CDN, nginx `proxy_cache`, Varnish, кэш фрагментов в приложении) решает,
«тот же ли это запрос», по ключу — обычно метод, хост, путь и query. Всё, что в
ключ не входит (заголовки, куки, тело, часть параметров), — «неключевые» входы.
Если приложение строит ответ из неключевого входа, злоумышленник один раз
получает ответ со своей подстановкой, кэш его сохраняет и раздаёт всем, кто
пришёл по тому же ключу. Безобидное отражение превращается в массовое XSS,
подмену скриптов или отказ в обслуживании.

## Где появляется в коде
- Абсолютные ссылки на ресурсы и редиректы из `request.url`, `request.base_url`,
  `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto`/`Scheme` (uvicorn
  `--proxy-headers` + `--forwarded-allow-ips="*"`) — на кэшируемых страницах.
- Шаблоны, которые вставляют заголовок/куку в HTML: язык из `Accept-Language`,
  тема из куки, `canonical`/`og:url` из текущего URL.
- Редирект на HTTPS, построенный по `X-Forwarded-Proto`, который кэшируется
  (301 по умолчанию кэшируется браузерами и CDN).
- Ответы-ошибки (400/404/500) с отражённым вводом, если кэш кэширует ошибки.
- `@lru_cache`/Redis-кэш HTML-фрагментов или JSON, ключ которого не учитывает
  все входы, влияющие на результат (пользователь, язык, хост).
- nginx: `proxy_cache_key` без `$host`/`$scheme`, `proxy_ignore_headers
  Cache-Control Set-Cookie`, `proxy_cache_valid any ...`.

Плохо:
```python
@app.get("/")
async def index(request: Request):
    base = f"{request.url.scheme}://{request.headers.get('x-forwarded-host', request.url.netloc)}"
    return templates.TemplateResponse("index.html", {"request": request, "cdn": base},
                                      headers={"Cache-Control": "public, max-age=600"})
```
Хорошо:
```python
PUBLIC_URL = settings.public_url                  # из env, фиксировано при деплое
return templates.TemplateResponse(..., {"cdn": PUBLIC_URL},
                                  headers={"Cache-Control": "no-store"})  # если страница не статика
```
Если ответ действительно зависит от заголовка — выставить `Vary: <заголовок>`
и убедиться, что кэш его соблюдает.

## Как искать
```
rg -n "x-forwarded-(host|proto|scheme|for)|X-Forwarded|forwarded-allow-ips|proxy-headers|ProxyHeadersMiddleware"
rg -n "request\.(url|base_url|headers\[|headers\.get)" app/ | rg -v "authorization|cookie"
rg -n "Cache-Control|max-age|public|s-maxage|Vary" app/ deploy/
rg -n "proxy_cache|proxy_cache_key|proxy_ignore_headers|proxy_cache_valid|fastcgi_cache|cache_key" deploy/ *.conf
rg -n "lru_cache|cachetools|aiocache|redis.*(get|set)" app/
```
Что смотреть в конфиге кэша/CDN:
- Из чего состоит ключ: есть ли `$host`, `$scheme`, полная query-строка?
- Какие параметры исключены из ключа (utm_*, «мусорные» параметры) и не читает ли
  их приложение.
- Кэшируются ли ответы с `Set-Cookie`, ошибки, редиректы, ответы на GET с телом.
- Уважает ли кэш `Cache-Control: private/no-store` и `Vary` от приложения или
  переопределяет TTL.
- Какие заголовки CDN по умолчанию пробрасывает к origin.

Вопросы ревьюера: какие заголовки/куки влияют на HTML или редирект? Входят ли они
в ключ? Может ли кто-то извне послать этот заголовок (или прокси его затирает)?

## Обходы, о которых забывают
- **«Кэш только для статики» — а статика динамическая.** JS/CSS, которые
  генерирует приложение (конфиг, локализация, ссылки с хостом), — кэшируются и
  могут нести отражённый ввод; CSS-ответ браузер может исполнить даже без
  строгого типа.
- **Неключевые заголовки, о которых не знаешь.** Фреймворк или прокси молча
  понимают `X-Forwarded-Host`, `X-Original-URL`, `X-HTTP-Method-Override` и
  подобные; приложение их не читает явно, но поведение меняется.
- **Исключённые из ключа параметры.** CDN игнорирует часть query (метки
  аналитики), а приложение использует полный URL — например, в `canonical`.
- **Расхождение парсинга query.** Кэш и фреймворк по-разному понимают
  разделители (`&`, `;`), дубли параметров и кодирование — значение «спрятано» в
  исключённом параметре для кэша, но читается приложением как ключевое.
- **Тело в GET.** Кэш ключует по строке запроса, а фреймворк читает параметры и
  из тела GET-запроса; плюс заголовки переопределения метода.
- **Нормализация ключа.** Кэш декодирует URL перед сравнением, браузер жертвы —
  нет: отражённый XSS, «невозможный» из-за кодирования в браузере, становится
  хранимым через кэш.
- **Инъекция в ключ.** Если кэш склеивает части ключа через разделитель без
  экранирования, два разных запроса могут получить один ключ.
- **Внутренние кэши без ключа.** Кэш фрагментов в приложении (`lru_cache` на
  функции, которая читает request) отравляется одним запросом сразу на всех
  страницах; «кэш-бастер» в query тут не изолирует.
- **«Это только self-XSS / только заголовок»** — именно кэш делает такие баги
  эксплуатируемыми против других; их всё равно надо чинить.
- **DoS через кэш.** Заголовок, ломающий ответ (ошибка, огромный редирект),
  закэшированный на главной, выключает сайт для всех.

## Как исправить правильно
1. Не кэшировать динамику: `Cache-Control: no-store` (или `private`) на всём, что
   генерирует приложение для людей; кэшировать только реально статичные файлы.
2. Абсолютные URL строить из `PUBLIC_URL` (env), а не из запроса.
3. `--forwarded-allow-ips` — только адрес своего прокси, не `*`; прокси
   безусловно перезаписывает `X-Forwarded-*` своими значениями.
4. Выключить ненужные заголовки-переопределения на прокси/во фреймворке;
   не принимать тело у GET.
5. Если ответ зависит от заголовка — добавить его в ключ или `Vary`, а не
   исключать из ключа «ради хит-рейта»; лучше переписать запрос на прокси.
6. Ключи внутренних кэшей — включают все входы функции (пользователь, хост,
   язык); не кэшировать персонализированный HTML.
7. Чинить отражения (XSS, отражение заголовков) даже если «они не эксплуатируемы».
8. Проверить настройки CDN по умолчанию: какие входы он не ключует.

## Ложные срабатывания
- Нет кэша между клиентом и приложением, а ответы помечены `no-store`.
- `request.url` используется только для логов/метрик или редиректа внутри того же
  пути с фиксированным хостом.
- `X-Forwarded-*` читается uvicorn только от доверенного IP прокси, а прокси
  перезаписывает их.
- `lru_cache` на чистой функции от конфига, без данных запроса.
