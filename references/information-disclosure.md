# Раскрытие информации (information disclosure)

## Суть
Приложение отдаёт то, что посторонним видеть не нужно: данные других пользователей,
секреты и ключи, внутреннее устройство (версии, пути, имена таблиц, исходники).
Само по себе это иногда безобидно, но часто это карта для следующей атаки или
прямая утечка ПД и ключей.

## Где появляется в коде
- Отладочный режим в проде: `debug=True`, трассировки в ответе, `/docs`, профилировщики,
  `/metrics`, `/debug`, `/admin` без входа.
- Обработчик исключений возвращает `str(exc)`/`traceback` клиенту; текст ошибки
  asyncpg/SQL уходит в JSON.
- Ответ API сериализует запись целиком (`dict(row)`, `SELECT *`), включая хеши,
  токены, email, внутренние флаги чужих пользователей.
- Разные ответы на «есть/нет» (учётки, объекты) — перечисление.
- Секреты в репозитории, `.env`, `config.yaml`, во фронтенд-бандле, в логах.
- Логирование тел запросов, токенов, заголовков `Authorization`, расшифровок/ПД.
- Отдача статики из корня проекта: `.git/`, бэкапы (`*.bak`, `~`, `.swp`), дампы.
- Комментарии разработчиков и скрытые ссылки в HTML/JS.
- Заголовки `Server`, `X-Powered-By`, версии в ошибках.

```python
# плохо
@app.exception_handler(Exception)
async def h(request, exc):
    return JSONResponse({"error": str(exc), "trace": traceback.format_exc()}, 500)

# хорошо: подробности — в лог (без ПД), клиенту — общий ответ с id для поддержки
@app.exception_handler(Exception)
async def h(request, exc):
    err_id = secrets.token_hex(6)
    log.exception("unhandled error id=%s path=%s", err_id, request.url.path)
    return JSONResponse({"error": "Внутренняя ошибка", "id": err_id}, 500)
```

```python
# плохо: вся строка в ответ
return dict(await db.fetchrow("SELECT * FROM users WHERE id=$1", uid))
# хорошо: явная выходная модель
class UserPublic(BaseModel): id: int; display_name: str
return UserPublic.model_validate(row, from_attributes=True)
```

Node/Express: `app.set('env','production')`, без `err.stack` в ответе, `helmet()` убирает
`X-Powered-By`; не отдавать `express.static('.')`.

## Как искать
```
rg -n 'debug\s*=\s*True|DEBUG\s*=\s*True|reload=True' .
rg -n 'traceback|format_exc|str\(e(xc)?\)|repr\(e' app/ | rg -i 'response|return|detail'
rg -n 'HTTPException\(.*detail=.*(e|exc|err)\b' app/
rg -n 'SELECT \*' app/ | rg -v migrations
rg -n 'dict\(row\)|dict\(r\)|\*\*row' app/
rg -n 'log(ger)?\.(info|debug|warning|error)\(.*(token|password|secret|authorization|transcript|body)' -i app/
rg -n 'StaticFiles\(directory=.\.?.\)|express\.static\(.\.' .
rg -n '(api[_-]?key|secret|token|password)\s*[:=]\s*["\x27][A-Za-z0-9_\-]{12,}' -i --hidden -g '!*.lock'
rg -n 'docs_url|redoc_url|openapi_url|/metrics|/debug' app/
git log -p --all -S 'API_KEY' --oneline | head      # секреты в истории
```
Вопросы ревьюера:
- Что видит клиент при необработанном исключении, ошибке валидации, ошибке БД,
  таймауте внешнего сервиса?
- Какие поля уходят в каждом ответе? Есть ли явные выходные модели, или
  сериализуется строка из БД?
- Что пишется в логи: тела запросов, токены, ПД, расшифровки? Кто имеет доступ к логам?
- Какие служебные эндпоинты доступны без входа в проде?
- Что отдаёт веб-сервер из файловой системы? Нет ли в выкладке `.git`, `.env`, бэкапов?
- Отличаются ли ответы (текст, статус, время, размер) для существующих и
  несуществующих объектов/учёток?

## Обходы, о которых забывают
- **«Безобидная» деталь.** Версия библиотеки, имя таблицы, внутренний путь, формат
  id — каждое по отдельности не секрет, но вместе дают точный план атаки.
- **Ошибка по нестандартному входу.** Обычные ответы чистые, но неверный тип,
  пустое тело, огромное число, другой `Content-Type` вызывают необработанное
  исключение с трассировкой.
- **Разница в поведении** вместо разницы в тексте: статус, время ответа, длина тела,
  наличие заголовка выдают существование учётки или объекта.
- **Чужие поля во вложенных объектах.** Свой объект возвращается правильно, но в нём
  лежит владелец/участники целиком — с почтой, ролями, токенами.
- **Служебные заголовки и методы.** Отладочные заголовки, `TRACE`/`OPTIONS`,
  заголовки прокси, раскрывающие внутренние адреса или данные аутентификации.
- **Исходники и история.** Папка `.git` или бэкап конфигурации в выкладке
  восстанавливают код и секреты, даже давно удалённые из текущей версии.
- **Клиентский код.** Ключи, «скрытые» админские роуты, флаги фич во фронтенд-бандле
  и source maps видны всем.
- **Кеши и индексация.** Ответ с ПД закеширован прокси/CDN или попал в `robots.txt`
  как «не индексировать /admin/…» — и тем самым раскрыт.

## Как исправить правильно
- Глобальный обработчик исключений: клиенту — общий текст и идентификатор, в
  серверный лог — подробности (без ПД и секретов). Отладочные страницы и
  `debug` — только в разработке.
- Явные выходные модели на каждый ответ; `SELECT` только нужных колонок;
  поля других пользователей — минимально необходимые.
- Единообразные ответы (текст, статус, по возможности время) там, где существование
  чувствительно; 404 и для «нет», и для «нельзя».
- Секреты только из env/секрет-хранилища; сканер секретов в CI; при утечке —
  перевыпуск ключа, а не только удаление из кода.
- Логи: маскировать токены и заголовки авторизации, не писать тела запросов и ПД.
- Выкладка без `.git`, `.env`, бэкапов и source maps; статика — из отдельной папки.
- Служебные эндпоинты (`/docs`, `/metrics`) — закрыть входом или сетью.
- `Cache-Control: no-store` для ответов с личными данными; убрать `Server`/
  `X-Powered-By`.
- Проверка на этапе сборки и ревью: что попадает в ответы, логи и выкладку.

## Ложные срабатывания
- `str(exc)` в логе (не в ответе) — нормально, если в исключении нет ПД/секретов.
- `SELECT *` во внутренней функции, результат которой дальше фильтруется выходной моделью.
- Строки, похожие на ключи, в тестах, фикстурах и примерах (`example`, `dummy`, `test`).
- Документация публичного API, открытая намеренно.
