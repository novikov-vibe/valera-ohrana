# NoSQL injection

## Суть
Недоверенные данные меняют смысл запроса к документной/ключ-значение базе (MongoDB,
CouchDB, Elasticsearch, Redis и т. п.). Два вида: **синтаксическая** — ввод ломает
строку запроса или JS-выражение; **операторная** — вместо скаляра клиент присылает
объект с операторами (`$ne`, `$gt`, `$regex`, `$where`), и фильтр начинает означать
другое. Последствия: обход входа, чтение чужих документов, перебор данных по символу,
DoS тяжёлыми регулярками, а при серверном JS — выполнение кода в базе.

## Где появляется в коде

**Python / pymongo, motor** — тело запроса целиком идёт в фильтр:
```python
# плохо: body — произвольный dict из JSON, может быть {"password": {"$ne": ""}}
user = await db.users.find_one({"email": body["email"], "password": body["password"]})
# хорошо: Pydantic-модель со строгими типами, сравнение хэша в коде
class Login(BaseModel):
    email: EmailStr
    password: str  # объект сюда не пройдёт — 422
user = await db.users.find_one({"email": data.email})
```
Опасно также:
- `$where`, `$function`, `$accumulator`, `mapReduce` со строкой, собранной из ввода;
- `{"name": {"$regex": user_input}}` без `re.escape` — и инъекция шаблона, и ReDoS;
- `find(json.loads(request.query_params["filter"]))` — клиент присылает готовый фильтр;
- `**request_dict` или `update_one(..., {"$set": body})` — клиент добавляет любые поля
  и операторы (`$set` на `role`, `$unset` и т. п.) — это ещё и mass assignment.

**Node/JS (Express + mongoose/mongodb)**: `qs`/`body-parser` превращают
`user[$ne]=x` в объект `{ $ne: "x" }`, поэтому `User.findOne({ user: req.query.user })`
уязвим даже без JSON. Mongoose до 6 без `strictQuery`/`sanitizeFilter` пропускал
операторы. Хорошо: `String(req.body.user)`, `mongoose.set('sanitizeFilter', true)`,
схемы валидации (zod/joi), `express-mongo-sanitize` — как дополнительный слой.

**Прочее**: Elasticsearch `query_string`/`script` с вводом, Redis `EVAL` со
склеенным Lua, CouchDB/Mango-селекторы из тела запроса, GraphQL-резолверы,
прокидывающие аргумент-объект прямо в фильтр.

## Как искать
```bash
rg -n "find(_one)?\(|aggregate\(|update_(one|many)\(|delete_(one|many)\(" --type py
rg -n "\\\$where|\\\$function|\\\$accumulator|\\\$expr|mapReduce|\\\$regex" 
rg -n "json\.loads\(.*(query|param|filter)" --type py
rg -n "\.(find|findOne|updateOne|deleteMany)\(\s*\{[^}]*req\.(body|query|params)" -g '*.{js,ts}'
rg -n "\\\$set\"?\s*:\s*(body|req\.body|data)" 
```
Вопросы ревьюера:
- Какой тип у каждого значения, попадающего в фильтр? Гарантирован ли скаляр
  (строка/число/UUID) до того, как он окажется в словаре запроса?
- Принимает ли эндпоинт фильтр/сортировку/проекцию целиком от клиента?
- Есть ли серверный JavaScript (`$where`) и отключён ли он в конфигурации базы?
- Можно ли превратить GET-параметр в объект (вложенные ключи с квадратными скобками)?
  Можно ли сменить Content-Type на JSON, чтобы прислать объект?

## Обходы, о которых забывают
- **Фильтр «ищем `$` в теле»** ломает легитимные значения и пропускает объект,
  пришедший через другой парсер (query-строка со скобками, form-data, вложенный JSON).
- **Проверка только строкового ввода**: разработчик экранирует кавычки, а атакующий
  присылает не строку, а объект — экранировать нечего, смысл фильтра уже другой.
- **Смена способа доставки**: если URL-параметр не превращается в объект, тот же
  эндпоинт может принять JSON-тело с тем же именем поля.
- **Обрезка условия**: в синтаксических инъекциях в JS-выражение спецсимволы
  (включая нулевой байт) позволяют «отбросить» хвост условия — например, проверку
  «опубликован ли документ».
- **Слепая выкачка**: даже если ответ лишь «найдено/не найдено», регулярка или
  JS-условие позволяет угадывать значение (в т. ч. имена полей и токены сброса пароля)
  по символу, а задержки дают канал по времени.
- **`$in` по списку имён** — перебор учётных записей за один запрос.

## Как исправить правильно
1. Строгая схема входа (Pydantic/zod): каждое поле фильтра — скалярного типа; лишние
   ключи запрещены (`model_config = ConfigDict(extra="forbid")`).
2. Фильтр строит сервер из отдельных значений; клиентские фильтры/сортировки — только
   через белый список полей и операторов.
3. Не использовать `$where`/`$function` с вводом; отключить серверный JS в MongoDB
   (`security.javascriptEnabled: false`), если не нужен.
4. Для поиска по подстроке — `re.escape()` и ограничение длины, либо полнотекстовый индекс.
5. Обновления — только явным списком полей, никогда `{"$set": body}`.
6. Защита в глубину: пользователь БД с минимумом прав, лимиты времени запроса
   (`maxTimeMS`), сверка пароля по хэшу в коде, а не в фильтре.

## Ложные срабатывания
- Значение прошло через Pydantic-поле типа `str`/`int`/`UUID` — объект туда не попадёт.
- `$regex`/`$in`/`$set` с константами или со значениями, собранными сервером
  (например, `{"$in": list_of_ids_from_db}`).
- Пайплайны агрегации, полностью заданные в коде, с параметрами-скалярами.
- Mongoose с включённым `sanitizeFilter` и схемой с типом `String` у поля.
