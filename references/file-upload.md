# File upload vulnerabilities

## Суть
Сервер принимает файл и недостаточно проверяет его имя, тип, содержимое, размер или
место хранения. В худшем случае загруженный файл исполняется как код (веб-шелл), в
остальных — перезаписывает чужие файлы (через имя), отдаётся другим пользователям как
HTML/SVG со скриптом (хранимый XSS), запускает XXE/SSRF при разборе, роняет сервер
огромным или «сжатым-бомбой» файлом, либо раскрывает содержимое через обработчики
(ImageMagick, ffmpeg, офисные конвертеры).

## Где появляется в коде

**Python / FastAPI `UploadFile`**:
```python
# плохо: имя и тип от клиента, полный файл в память, путь из имени
data = await file.read()
if file.content_type.startswith("audio/"):          # заголовок задаёт клиент
    (UPLOAD_DIR / file.filename).write_bytes(data)  # путь и перезапись
# хорошо
MAX = 500 * 1024 * 1024
ALLOWED = {".mp3": "audio/mpeg", ".wav": "audio/wav", ".m4a": "audio/mp4"}
ext = Path(file.filename or "").suffix.lower()
if ext not in ALLOWED: raise HTTPException(415)
dest = TMP_DIR / f"{uuid4()}{ext}"                  # имя генерирует сервер
size = 0
async with aiofiles.open(dest, "wb") as out:
    while chunk := await file.read(1 << 20):
        size += len(chunk)
        if size > MAX: ...удалить, 413
        await out.write(chunk)
# затем проверить содержимое (сигнатура + реальный разбор: ffprobe/Pillow),
# и только после — перенести в постоянное хранилище, записать в БД
```
Дополнительно:
- лимит размера тела на уровне прокси (nginx `client_max_body_size`) — FastAPI сам
  не ограничивает; `await file.read()` без лимита держит всё в памяти;
- отдача файлов: `FileResponse` с `Content-Type` из сохранённого значения клиента и
  `inline` — путь к XSS; ставить тип по своему белому списку, `Content-Disposition:
  attachment` для неизвестного, `X-Content-Type-Options: nosniff`;
- обработка: Pillow (лимит пикселей `Image.MAX_IMAGE_PIXELS`), ffmpeg/ffprobe
  (протоколы плейлистов `concat`/`http` в медиа — SSRF/чтение файлов: задавать
  `-protocol_whitelist file` и формат явно), ImageMagick (политики, отключённые
  кодеры MSL/MVG/URL), LibreOffice, `python-docx` (XXE), архивы (Zip Slip, бомбы).

**Node/JS**: `multer` с `filename` = `originalname`, `express.static` на каталог
загрузок, проверка только `mimetype`. **PHP/IIS/Apache**: загрузка в веб-корень, где
расширение определяет исполнение — классический веб-шелл.

## Как искать
```bash
rg -n "UploadFile|File\(\.\.\.\)|\.filename\b|\.content_type\b" --type py
rg -n "await \w+\.read\(\)" --type py                         # чтение без лимита
rg -n "write_bytes\(|shutil\.copyfileobj\(|aiofiles\.open\(" --type py
rg -n "FileResponse\(|StreamingResponse\(|media_type\s*=" --type py
rg -n "multer|originalname|mimetype|express\.static" -g '*.{js,ts}'
rg -n "client_max_body_size" -g '*.conf'
```
Вопросы ревьюера:
- Кто задаёт имя файла на диске, расширение и `Content-Type` при отдаче?
- Где файл лежит до проверки и доступен ли он оттуда по HTTP?
- Чем проверяется содержимое — заголовком, сигнатурой или реальным разбором?
- Какие внешние программы разбирают файл и с какими правами/лимитами?
- Есть ли лимит размера, числа файлов, длительности (для аудио) и квоты на пользователя?
- Отдаётся ли файл с того же домена, что и приложение (риск XSS через HTML/SVG)?

## Обходы, о которых забывают
- **Доверие `Content-Type` запроса**: этот заголовок части формы задаёт клиент;
  проверка по нему ничего не гарантирует.
- **Чёрный список расширений** всегда неполон: у серверов много альтернативных
  исполняемых расширений, а регистр, двойные расширения, хвостовые точки и пробелы,
  кодирование, нулевой байт и Unicode-аналоги символов по-разному понимаются
  валидатором и сервером/ОС.
- **Загрузка файла конфигурации**: если можно положить файл настроек сервера
  (`.htaccess`, `web.config`) в каталог загрузок, он переназначит, какие расширения
  исполнять, — и чёрный список становится бесполезен.
- **Проверка сигнатуры/размеров картинки** не исключает полезной нагрузки: файл
  может быть одновременно валидной картинкой и скриптом (полиглот), код прячется в
  метаданных. Значимо только то, как файл будет потом интерпретирован.
- **Гонка**: файл сначала пишется в публичный каталог, проверяется, затем удаляется —
  в этом окне его можно запросить. Аналогично для загрузки «по URL» с предсказуемым
  временным именем.
- **Альтернативные пути записи**: включённый HTTP `PUT`/WebDAV, отдельный API для
  мобильного клиента, импорт из архива — без тех же проверок.
- **Путь в имени файла** (`../`) — см. `path-traversal.md`; сервер может «исправить»
  расширение, но не каталог.
- **Безобидные форматы с активным содержимым**: SVG и HTML (скрипты), PDF, офисные
  документы (XXE, макросы), медиаплейлисты (обращение к файлам/сети при разборе).

## Как исправить правильно
1. Белый список расширений **и** проверка содержимого реальным разбором нужным
   декодером; расширение и тип при отдаче задаёт сервер по своему словарю.
2. Имя на диске — сгенерированное (UUID); исходное имя — только как метаданные в
   БД, экранированное при выводе.
3. Сначала во временный каталог вне веб-корня → проверка → перенос; хранилище без
   права исполнения (отдельный том/бакет, `noexec`), отдача через приложение с
   проверкой доступа, а не статикой.
4. Лимиты: размер на прокси и в коде (потоковое чтение), число файлов, длительность,
   пиксели, коэффициент распаковки; таймауты обработчиков.
5. Отдача: `Content-Disposition: attachment` для всего, кроме явно безопасных типов,
   `nosniff`, строгий CSP, при возможности — отдельный домен для пользовательского
   контента.
6. Обработчики (ffmpeg, ImageMagick, LibreOffice) — в изоляции, без сети и секретов,
   с ограниченными протоколами и политиками; антивирус — как дополнительный слой.
7. Отключить ненужные HTTP-методы (`PUT`, `DELETE`, WebDAV).

## Ложные срабатывания
- `file.filename` используется только для логов/метаданных (не для пути) и
  экранируется при выводе в HTML.
- `file.content_type` читается для информации, а решение принимает разбор содержимого.
- `await file.read()` при заранее ограниченном размере тела на прокси и маленьком лимите.
- Загрузка в объектное хранилище под сгенерированным ключом с отдачей через
  подписанные ссылки и принудительным `Content-Disposition`.
