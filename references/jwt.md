# JWT (JSON Web Token)

## Суть
JWT — подписанный набор утверждений (кто пользователь, роль, срок), который сервер
принимает без похода в базу. Вся безопасность держится на проверке подписи: если
сервер её не проверяет, проверяет «по указке» самого токена или подписывает слабым
ключом, клиент сам выписывает себе любую личность и любые права.

## Где появляется в коде
- `jwt.decode(token, options={"verify_signature": False})` или `get_unverified_claims`
  — и дальше эти данные используются для доступа.
- `algorithms` не передан или берётся из заголовка токена (`jwt.get_unverified_header`).
- Один ключ для разных алгоритмов (публичный RSA-ключ передаётся в общий `decode`
  вместе со списком, где есть и `HS256`, и `RS256`).
- Секрет HMAC — `"secret"`, `"changeme"`, имя проекта, пример из README, короткая строка.
- Ключ ищется по `kid` из токена: путь к файлу, SQL-запрос, словарь без allowlist.
- Ключи загружаются по `jku`/`x5u` из токена, или доверяется встроенному `jwk`/`x5c`.
- Нет `exp`/`aud`/`iss` или они не проверяются; нет отзыва при выходе.
- Токен в URL (`?token=`), в логах, в `localStorage`.

```python
# плохо
claims = jwt.decode(token, options={"verify_signature": False})
alg = jwt.get_unverified_header(token)["alg"]
claims = jwt.decode(token, KEY, algorithms=[alg])

# хорошо (PyJWT): алгоритм зафиксирован сервером, обязательные утверждения проверяются
claims = jwt.decode(
    token, PUBLIC_KEY, algorithms=["RS256"],
    audience="app-api", issuer="https://auth.example",
    options={"require": ["exp", "iat", "sub", "aud", "iss"]},
)
```

```python
# плохо: kid прямо в путь / в запрос
key = open(f"keys/{header['kid']}").read()
# хорошо: kid — только ключ словаря заранее загруженных ключей
key = TRUSTED_KEYS.get(header["kid"]) or reject()
```

Node (`jsonwebtoken`): `jwt.verify(t, key, {algorithms: ['RS256'], audience, issuer})`;
`jwt.decode()` не проверяет подпись вообще. `jose`: `jwtVerify(t, JWKS, {algorithms, issuer, audience})`.

## Как искать
```
rg -n 'verify_signature.*False|get_unverified_(claims|header)|jwt\.decode\(' app/
rg -n 'algorithms\s*=' app/                   # есть ли везде и что в списке
rg -n 'HS256|HS384|HS512' app/ config*        # где секрет и какой длины
rg -n 'JWT_SECRET|SECRET_KEY|signing_key' -g '!*.lock'
rg -n '\bkid\b|\bjku\b|\bx5u\b|\bjwk\b|\bx5c\b' app/
rg -n 'jwt\.decode\(|\.decode\(token' src/    # Node: decode вместо verify
rg -n 'token=|\?jwt=|access_token=' app/ templates/
```
Вопросы ревьюера:
- Каждый путь, где из токена читается `sub`/роль, — проходит ли он через функцию с
  проверкой подписи? Нет ли «быстрого» пути через decode без проверки?
- Кто выбирает алгоритм — сервер или токен? Сколько алгоритмов разрешено и одного
  ли они семейства?
- Откуда ключ: env/секрет-хранилище? Какова его энтропия? Совпадает ли он между
  стендами?
- Какие заголовки токена влияют на выбор ключа? Есть ли allowlist?
- Срок жизни, `aud`, `iss` — проверяются? Как отзывается токен при выходе, смене
  пароля, увольнении?

## Обходы, о которых забывают
- **Decode вместо verify.** Во многих библиотеках есть функция «просто распаковать»;
  если код по ошибке использует её, подпись не значит ничего.
- **Алгоритм `none`.** Старые или плохо настроенные библиотеки принимают неподписанный
  токен. Фильтр по точной строке обходится вариациями регистра — поэтому нужен
  allowlist, а не blocklist.
- **Путаница алгоритмов.** Сервер ожидает асимметричную подпись и передаёт в общую
  функцию проверки публичный ключ. Если токен заявит симметричный алгоритм,
  библиотека использует тот же публичный ключ как HMAC-секрет — а он публичен.
  Публичный ключ к тому же можно получить из JWKS или вычислить по паре токенов.
  Спасает только фиксированный сервером алгоритм.
- **Слабый секрет HMAC** перебирается офлайн по одному перехваченному токену —
  лимиты запросов здесь не помогают.
- **Ключ, предложенный самим токеном.** Встроенный `jwk`/`x5c` или ссылка `jku`/`x5u`
  позволяют подписать своим ключом. Фильтр хостов для `jku` ломается расхождениями
  парсинга URL и открытыми редиректами на доверенном домене.
- **`kid` как путь или SQL.** Обход каталога к файлу с известным содержимым
  (например, пустому) превращает его в ключ; `kid` в запросе к БД — SQL-инъекция.
- **Прочие заголовки** (`cty`) после обхода подписи открывают путь к парсерам XML и
  десериализации.
- **«Не можем отозвать».** Украденный долгоживущий токен работает до `exp`, выход
  ничего не делает.
- **JWT не шифрует.** Содержимое читает любой: в утверждения нельзя класть ПД и секреты.
- **Токен для другого сервиса.** Без проверки `aud` токен, выписанный для соседнего
  приложения с тем же издателем, принимается нашим.

## Как исправить правильно
- Одна функция проверки токена, через которую проходят все роуты; decode без
  проверки — запрещён (линтер/grep в CI).
- Алгоритм — из конфига сервера, список из одного элемента; разные алгоритмы — разные
  ключи и разные функции.
- Секрет HMAC ≥256 бит из CSPRNG, только из env; лучше асимметричные ключи.
- `kid` — только индекс в заранее загруженном наборе доверенных ключей; `jku`/`jwk`/
  `x5c`/`x5u` из токена игнорировать.
- Обязательные `exp` (короткий срок), `iat`, `aud`, `iss`, `sub`; небольшой допуск часов.
- Отзыв: короткие access-токены + серверные refresh-токены, денайлист по `jti`, версия
  сессии в БД, которую можно увеличить.
- Хранение в браузере: для веба часто проще и надёжнее серверная сессия с cookie
  `HttpOnly`; если JWT — в `HttpOnly`-cookie, не в `localStorage`; никогда в URL.
- Обновлять библиотеку; читать её документацию по безопасным значениям по умолчанию.

## Ложные срабатывания
- `get_unverified_header` только для выбора `kid` из allowlist перед полноценной проверкой.
- `decode` без проверки в тестах или в отладочном выводе, не влияющем на доступ.
- `HS256` с длинным случайным ключом из env — допустимо, если алгоритм зафиксирован.
