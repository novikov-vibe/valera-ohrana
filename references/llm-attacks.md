# Атаки на веб-интеграции LLM

## Суть
Модель не различает «инструкции» и «данные»: всё в контексте — просто текст.
Поэтому любой недоверенный текст, попавший в промпт (сообщение пользователя,
расшифровка созвона, сообщение из чата, письмо, веб-страница, ответ API), может
переписать поведение модели — это prompt injection, прямая или косвенная.
Опасность определяется не моделью, а тем, что приложение делает с её выводом:
рендерит как HTML, исполняет, передаёт в SQL/шелл/URL или вызывает по нему
инструменты с правами сервиса. Модель — это пользователь без прав, которому
нельзя верить.

## Где появляется в коде
- Сборка промпта из недоверенных данных: расшифровки (речь любого участника),
  входящие сообщения Mattermost (`chat_inbox`), письма, описания событий
  календаря, задачи YouTrack, загруженные документы, страницы по ссылке.
- Вывод модели в HTML: `Markup(llm_text)`, `|safe` в Jinja2, `innerHTML`,
  Markdown-рендер с сырым HTML и автозагрузкой картинок.
- Вывод модели как код/команда/запрос: `eval`, `exec`, `subprocess(..., shell=True)`,
  f-строка в SQL, путь к файлу, URL для `httpx.get`.
- Инструменты (function calling) с правами сервиса: «отправить сообщение»,
  «создать задачу», «изменить выжимку», «получить созвон по id» — без проверки,
  что *текущий пользователь* имеет на это право.
- Автоматические действия по выводу модели без участия человека (отправка в
  чат, создание задач, рассылки).
- Ссылки и упоминания, сгенерированные моделью, в сообщениях бота (`@channel`,
  ссылки на чужие домены, Markdown-картинки с данными в URL).
- В контекст кладутся данные, которые текущему пользователю видеть нельзя
  (чужие созвоны, системные ключи в системном промпте).

Плохо:
```python
summary = await llm(f"Сделай выжимку:\n{transcript}")          # transcript — недоверенный
return HTMLResponse(markdown(summary))                          # сырой HTML из модели
tool = json.loads(resp)["tool"]; await TOOLS[tool](**args)      # любой инструмент, права сервиса
```
Хорошо:
```python
msgs = [{"role": "system", "content": SYSTEM},                   # из config.yaml
        {"role": "user", "content": "<transcript>\n" + transcript + "\n</transcript>"}]
data = SummarySchema.model_validate_json(resp)                   # строгая схема, без свободного HTML
html = jinja_env.from_string("{{ text }}").render(text=data.text)   # автоэкранирование
# инструменты: белый список, проверка прав пользователя, кнопка человека для изменяющих
await require_access(user, call.meeting_id)                       # то же правило, что и у веба
```
Разметка `<transcript>` — гигиена, а не защита: границу обеспечивают схема
вывода, права и подтверждение человеком.

## Как искать
```
rg -n "chat\.completions|messages\s*=|ChatCompletion|deepseek|openai|anthropic|llm\(" app/
rg -n "f\".*\{(transcript|text|message|body|content|email)\}" app/   # недоверенное в промпт
rg -n "\|\s*safe|Markup\(|innerHTML|dangerouslySetInnerHTML|markdown\(" app/ templates/
rg -n "eval\(|exec\(|shell=True|os\.system|text\(f\"|execute\(f\"" app/
rg -n "tools\s*=|tool_calls|function_call|TOOLS\[" app/
rg -n "!\[.*\]\(|<img" app/                                            # картинки из вывода модели
```
Вопросы ревьюера:
- Перечислить все входы модели: какие из них может написать посторонний
  (участник созвона, отправитель письма, автор задачи)?
- Что модель может *сделать*: какие инструменты, с чьими правами? Проверяется ли
  право нажавшего пользователя вне модели?
- Куда идёт вывод: HTML, Markdown с картинками, чат, SQL, файлы, URL?
- Есть ли в контексте данные, которые текущему пользователю видеть нельзя?
- Какие действия происходят без подтверждения человека?

## Обходы, о которых забывают
- **Косвенная инъекция через данные.** Злоумышленнику не нужен доступ к чату с
  моделью: достаточно сказать фразу на созвоне, написать в канал, прислать
  письмо или вписать текст в описание задачи, которое модель потом обработает от
  имени жертвы.
- **«Системный промпт запрещает» / «модель сама откажется».** Инструкции в
  промпте — пожелание, а не граница доступа; их обходят переформулировкой,
  ролевыми сценариями, многошаговым диалогом, перебором вариантов.
- **Фильтр по ключевым словам.** Инструкцию можно перефразировать, перевести,
  закодировать (base64, hex), разбить невидимыми Unicode-символами, исказить
  буквы — смысл для модели сохраняется, regex промахивается.
- **Поддельная разметка.** Внутри данных можно изобразить «конец документа»,
  «реплику пользователя» или «системное сообщение» — модель часто ведётся.
- **Безобидные инструменты в цепочке.** Инструмент «прочитать файл по имени» или
  «поиск» превращается в path traversal / SQL-инъекцию, если модель передаёт
  туда аргументы, а код доверяет им как своим.
- **Утечка через рендер.** Markdown-картинка или ссылка, которую сгенерировала
  модель, с данными в URL — браузер сам отправит их наружу при отображении, клик
  не нужен.
- **Вывод модели = пользовательский ввод.** XSS, SSRF, SQL-инъекции возвращаются
  через «доверенный» вывод модели.
- **Права сервиса.** Инструмент выполняется с ключом бота/сервисного аккаунта,
  поэтому модель «может» больше, чем пользователь, за которого она работает.
- **Утечка контекста.** Модель пересказывает системный промпт, чужие данные из
  RAG, ключи — всё, что положено в контекст, считать доступным собеседнику.

## Как исправить правильно
1. Всё, что модель может вызвать, — считать публичным API: аутентификация и
   проверка прав *пользователя* (то же правило доступа, что у веба) в коде
   инструмента, а не в промпте.
2. Минимум инструментов и функций, минимум прав; без открытых инструментов
   «выполнить запрос/шелл/URL»; изменяющие и внешние действия — только по кнопке
   человека (как создание задачи в YouTrack).
3. Вывод — по строгой схеме (JSON + валидация), факты проверять кодом (цитаты и
   тайм-коды искать по расшифровке, а не верить модели).
4. Рендер — с автоэкранированием; Markdown без сырого HTML, ссылки только на
   разрешённые домены, внешние картинки не загружать; CSP.
5. Никогда не `eval`/`shell`/SQL-строки из вывода; параметризованные запросы,
   фиксированные пути.
6. В контекст класть только то, что разрешено видеть текущему пользователю;
   секретов в промпте нет.
7. Отделять недоверенные данные от инструкций (роль, разметка) — как гигиена;
   фильтры и модель-классификатор — дополнительный слой, не основной.
8. Таймауты, лимиты токенов и частоты, логирование решений без ПД.

## Ложные срабатывания
- Недоверенный текст идёт в модель, а вывод только показывается как
  экранированный текст тому же пользователю и ничего не вызывает.
- Модель выбирает значение из закрытого перечисления, которое валидирует код.
- Инструменты только читают данные, уже доступные этому пользователю, с
  проверкой доступа в коде.
