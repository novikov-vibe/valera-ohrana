# Web cache deception (обман кэша)

## Суть
Обратная сторона отравления: злоумышленник не подменяет ответ, а заставляет кэш
сохранить чужой личный ответ. Жертве подсовывают ссылку, которая для кэша
выглядит как статика (по расширению, папке или имени файла), а приложение
отдаёт по ней обычную персональную страницу. Кэш сохраняет её как публичную, и
злоумышленник читает по той же ссылке чужие данные: расшифровки, токены, CSRF-
токены, ключи API на странице настроек.

## Где появляется в коде
- Страницы и API с личными данными без `Cache-Control: no-store`/`private`
  (по умолчанию FastAPI не ставит заголовки кэша вовсе).
- Роутинг, «прощающий» лишнее в пути: `/{path:path}`, catch-all для SPA,
  отдача `index.html` на любой неизвестный путь, `redirect_slashes`,
  обработка `;` (matrix-параметры) и `%2F`.
- Правила кэша в nginx/CDN по расширению или префиксу:
  `location ~* \.(css|js|png|ico)$ { proxy_cache ...; }`,
  `location /static/ { proxy_cache ... }` при том, что `/static/` проксируется
  в приложение, а не отдаётся с диска.
- Правила «кэшировать всё, независимо от заголовков origin»
  (`proxy_ignore_headers Cache-Control`, CDN «Cache Everything»).
- Отдача файлов (аудио, вложения) через приложение по пути, который кэш
  считает статикой.

Плохо:
```nginx
location ~* \.(css|js|jpg|png|ico|mp3)$ {
    proxy_pass http://app;          # статики на диске нет — всё уходит в приложение
    proxy_cache static;
    proxy_ignore_headers Cache-Control Set-Cookie;
    proxy_cache_valid 200 1d;
}
```
Хорошо:
```nginx
location /static/ { alias /srv/app/static/; }   # статика с диска, мимо приложения
location / { proxy_pass http://app; }            # без proxy_cache для динамики
```
```python
@app.middleware("http")
async def no_store(request, call_next):
    resp = await call_next(request)
    if not request.url.path.startswith("/static/"):
        resp.headers.setdefault("Cache-Control", "no-store, private")
    return resp
```

## Как искать
```
rg -n "proxy_cache|fastcgi_cache|cache_key|proxy_ignore_headers|Cache Everything|cache_rules" deploy/ *.conf Caddyfile
rg -n "location ~\*? .*\\\.(css|js|png|jpg|ico|svg|woff)" deploy/
rg -n "\{[a-z_]+:path\}|catch_all|spa_fallback|redirect_slashes" app/
rg -n "Cache-Control" app/                     # где заголовки ставятся, а где нет
rg -n "FileResponse|StreamingResponse|StaticFiles" app/
```
Что смотреть в конфиге кэша/CDN:
- По каким признакам кэш решает «это статика»: расширение, префикс папки,
  точное имя (`robots.txt`, `favicon.ico`).
- Уважает ли кэш `Cache-Control` origin или переопределяет его.
- Нормализует ли кэш путь (декодирование `%2F`, `%2E`, разрешение `..`) так же,
  как приложение/фреймворк.
- Какие символы кэш считает концом пути, а какие — приложение.
- Сверяет ли CDN `Content-Type` ответа с расширением (защита «cache deception
  armor» и аналоги).

Вопросы ревьюера: что вернёт приложение на «личный путь + `/x.css`», «личный
путь + `;x.css`», «личный путь + `%2Fx.css`»? 200 с личной страницей — плохой
знак, если кэш перед ним работает по расширению.

## Обходы, о которых забывают
- **Лишние сегменты пути.** Фреймворк с параметрами пути или catch-all
  игнорирует хвост и отдаёт личную страницу, а кэш видит путь, оканчивающийся
  «статическим» расширением.
- **Разделители.** Символ, который для приложения обрывает путь (`;`, точка в
  некоторых фреймворках, закодированный нулевой байт, закодированные `?`/`#`),
  для кэша — обычная часть пути. Приложение видит личный эндпоинт, кэш — файл.
- **Нормализация.** Если одна сторона декодирует `%2F` и схлопывает `..`, а
  другая нет, путь, который для кэша лежит «в /static/», для приложения ведёт на
  личную страницу — или наоборот, при участии дополнительного разделителя.
- **Правила по точному имени** (robots.txt, favicon) эксплуатируются только если
  кэш нормализует путь, а приложение нет — но такие правила тоже надо проверять.
- **«У нас есть `Cache-Control: private`»** — бесполезно, если CDN/правило
  его игнорирует.
- **API тоже страницы.** JSON с токенами/личными данными по `/api/...` так же
  кэшируется, если правило кэша матчится.
- **Это не требует XSS или кражи сессии**: жертва просто открывает ссылку
  залогиненной.

## Как исправить правильно
1. На всех динамических ответах — `Cache-Control: no-store, private` (middleware,
   а не в каждом роуте); для персональных файлов (аудио) — тоже `private`.
2. Кэш/CDN не переопределяет заголовки origin; правило «кэшировать всё» не
   применяется к путям, которые проксируются в приложение.
3. Статику отдавать с диска отдельным `location`/`StaticFiles`, кэшировать
   только её.
4. Строгий роутинг: без catch-all на личных разделах, 404 на неизвестный хвост
   пути, не принимать `;`-параметры и закодированные слэши, если они не нужны.
5. Согласовать нормализацию путей у кэша и приложения (или выключить её на
   одной стороне так, чтобы они совпадали).
6. Включить проверку соответствия `Content-Type` и расширения в CDN, если есть.

## Ложные срабатывания
- Перед приложением нет кэширующего слоя (только TLS-терминатор без
  `proxy_cache`), а браузерный кэш личных страниц закрыт `no-store`.
- Правило кэша на `/static/`, который физически отдаётся с диска и в
  приложение не проксируется.
- Публичные страницы без личных данных и без токенов.
