# Clickjacking (UI redressing)

## Суть
Чужая страница загружает наш сайт в невидимый или замаскированный iframe и
подставляет под курсор пользователя нашу кнопку. Пользователь думает, что
нажимает что-то на чужом сайте, а на деле подтверждает действие у нас — с
собственной сессией. CSRF-токены тут не помогают: запрос идёт изнутри нашей
же страницы и токен в нём настоящий. Защита — запретить встраивание в чужие
фреймы.

## Где появляется в коде
**Нет заголовков запрета встраивания.** Ни `Content-Security-Policy:
frame-ancestors`, ни `X-Frame-Options` на HTML-ответах.

```python
# хорошо: middleware на все ответы
@app.middleware("http")
async def security_headers(request, call_next):
    resp = await call_next(request)
    resp.headers.setdefault("Content-Security-Policy", "frame-ancestors 'none'")
    resp.headers.setdefault("X-Frame-Options", "DENY")
    return resp
```

**Заголовки только на части страниц.** Выставлены в одном роуте/шаблоне, а
страницы подтверждения, настройки, админка, ошибки — без них.

**Попытка через `<meta>`.**
```html
<!-- не работает: браузер игнорирует X-Frame-Options в meta,
     frame-ancestors тоже не применяется из meta -->
<meta http-equiv="X-Frame-Options" content="DENY">
```

**JS-защита от фреймов** (`if (top !== self) top.location = self.location`) как
единственная мера.

**Состояние из URL.** Страница принимает предзаполнение формы через GET-параметры
(«поделиться», «назначить ответственного», «удалить по ссылке») — во фрейме
атакующему остаётся добиться одного клика.

**Однокликовые опасные действия:** удалить созвон, выдать доступ, отозвать
интеграцию, «Разрешить» в OAuth-согласии.

**Браузерные расширения.** Страницы расширения, перечисленные в
`web_accessible_resources` с `matches: ["<all_urls>"]`, можно встроить в любой
сайт; если там есть кнопки с правами расширения — это тот же clickjacking.
Оверлей, который content script вставляет в чужую страницу, тоже может быть
перекрыт элементами самой страницы.

## Как искать
```bash
rg -n 'frame-ancestors|X-Frame-Options' 
rg -n 'http-equiv=["\x27]?(X-Frame-Options|Content-Security-Policy)' -i -g '*.html'
rg -n 'top\s*!==?\s*self|top\.location|self\s*!==?\s*top|window\.top' -t js -g '*.html'
rg -n 'web_accessible_resources' -g 'manifest.json'
rg -n 'add_middleware|@app\.middleware' -t py
```
Проверка ответа: `curl -sI https://host/page | rg -i 'frame|content-security'`
для нескольких разных страниц, включая страницы ошибок и за прокси.

Вопросы ревьюера:
- Заголовок ставится централизованно (middleware/прокси) или по месту?
- Не срезает ли его reverse-proxy/CDN? Проверено ли на выкладке, а не только локально?
- Нужно ли сайту вообще встраиваться куда-то? Если да — куда именно?
- Какие действия выполняются одним кликом и можно ли предзаполнить их из URL?

## Обходы, о которых забывают
- **JS-«фреймобойки» отключаются:** у iframe есть атрибут `sandbox`, который
  может разрешить скрипты и формы, но запретить навигацию верхнего окна —
  скрипт либо не может проверить, где он, либо не может уйти из фрейма, а
  сама страница продолжает работать. Ещё варианты — двойное встраивание,
  блокировка навигации через диалоги ухода со страницы, отключённый JS.
- **`ALLOW-FROM` в X-Frame-Options** современными браузерами не поддерживается
  и в них «открывается» — защиты нет вовсе.
- **X-Frame-Options принимает одно значение** — нельзя разрешить и себя, и
  партнёра; для этого нужен `frame-ancestors` со списком.
- **`frame-ancestors` с маской `*.domain`** не покрывает сам `domain` —
  его нужно указать отдельно; и наоборот, маска даёт доступ всем поддоменам.
- **Meta-теги не работают** ни для одного из механизмов — только HTTP-заголовок.
- **SameSite-cookie частично помогают** (во фрейме чужого сайта cookie не
  уйдут), но соседний поддомен считается тем же сайтом, а страницы без входа не
  защищены никак.
- **Многошаговые сценарии** (несколько кликов, перетаскивание) тоже реальны —
  «нужно много действий» не аргумент.
- **Сочетание с DOM-XSS:** если XSS срабатывает по клику во фрейме, clickjacking
  становится средством доставки.
- **Double-clickjacking** (подмена окна между двумя кликами) идёт в окне верхнего
  уровня — заголовки против фреймов его не останавливают; для критичных действий
  нужна серверная авторизация операции, а не ещё одна кнопка «Подтвердить».

## Как исправить правильно
1. На всех HTML-ответах: `Content-Security-Policy: frame-ancestors 'none'`
   (или `'self'`, или точный список origin), плюс `X-Frame-Options: DENY`
   (`SAMEORIGIN`) для старых браузеров.
2. Ставить в одном месте — middleware или reverse-proxy, и проверять
   на реальной выкладке, что заголовок доходит.
3. Не принимать предзаполнение опасных действий из GET-параметров; опасные
   действия — через POST с CSRF-защитой.
4. Для необратимых действий — повторный ввод/подтверждение на сервере.
5. Сессионная cookie `SameSite=Lax`/`Strict` как дополнительный слой.
6. Расширение: `web_accessible_resources` — минимальный набор файлов и
   узкие `matches`; оверлей content script — в Shadow DOM с максимальным
   `z-index`, критичные действия не одним кликом.

## Ложные срабатывания
- Отсутствие заголовков на не-HTML ответах (JSON, картинки, аудио) — их
  встраивание во фрейм не даёт кликабельного интерфейса.
- Страницы, которые по задаче встраиваются (виджеты), если `frame-ancestors`
  содержит точный список и на них нет опасных действий.
- Заголовок не виден в коде приложения, но ставится прокси (проверить
  фактическим запросом).
