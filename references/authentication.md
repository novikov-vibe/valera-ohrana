# Аутентификация: пароли, 2FA, сброс пароля, сессии

## Суть
Аутентификация отвечает на вопрос «кто это». Уязвимости появляются, когда механизм
поддаётся перебору, раскрывает существование учёток или содержит логическую дыру,
позволяющую пропустить шаг. Итог — вход под чужим именем, вплоть до админа, без
знания пароля.

## Где появляется в коде
- Разные ответы на «нет такого пользователя» и «неверный пароль» (текст, код, время).
- Сравнение хешей через `==`, хранение паролей в MD5/SHA без соли, `bcrypt` с
  молчаливым обрезанием до 72 байт.
- Лимит попыток по IP или сброс счётчика при любом успешном входе.
- 2FA: после пароля уже ставится полноценная сессия; пользователь второго шага берётся
  из cookie/поля формы, а не из серверного состояния.
- Сброс пароля: токен из `random`/времени/`uuid1`, без срока, многоразовый; ссылка
  собирается из `request.headers["host"]`/`request.base_url`.
- «Запомнить меня» — cookie из имени пользователя, времени или хеша пароля.
- Сессия: id не меняется после входа, logout только стирает cookie на клиенте,
  нет `Secure/HttpOnly/SameSite`.

```python
# плохо
user = await db.fetchrow("SELECT * FROM users WHERE email=$1", email)
if not user: return JSONResponse({"error": "no such user"}, 404)
if hashlib.sha256(pw.encode()).hexdigest() != user["pw"]: return JSONResponse({"error": "bad password"}, 401)

# хорошо: одинаковый ответ и время, медленный хеш, постоянное сравнение внутри библиотеки
ok = verify_password(pw, user["pw_hash"] if user else DUMMY_HASH)  # argon2/bcrypt
if not (user and ok): raise HTTPException(401, "Неверный логин или пароль")
```

```python
# плохо: ссылка сброса из заголовка Host
link = f"{request.base_url}reset?token={token}"
# хорошо: адрес из конфигурации
link = f"{settings.PUBLIC_URL}/reset?token={token}"
token = secrets.token_urlsafe(32)          # хранить в БД хешем, срок 15–60 мин, одноразовый
```

Node: `crypto.randomBytes(32)` вместо `Math.random()`; `crypto.timingSafeEqual`;
`express-session` с `cookie: {secure, httpOnly, sameSite}` и `req.session.regenerate()`
после входа.

## Как искать
```
rg -n 'random\.(random|randint|choice)|uuid1|time\.time\(\)' app/ | rg -i 'token|code|otp|reset'
rg -n 'md5|sha1|sha256\(' app/ | rg -i 'pass'
rg -n '== *(user|row)\[.*(pass|hash|token|code)' app/
rg -n 'base_url|headers\[.host.\]|url_for\(' app/ | rg -i 'reset|verify|invite|link'
rg -n 'set_cookie\(' app/                      # проверить secure/httponly/samesite
rg -n 'remember|otp|totp|2fa|mfa|verification_code' app/
rg -n 'Math\.random|===.*password' src/
```
Вопросы ревьюера:
- Что меняется в ответе (текст, статус, время, заголовки) для существующей и
  несуществующей учётки — на входе, регистрации, сбросе пароля?
- Где и по какому ключу считаются неудачные попытки? Что их сбрасывает?
- Какое состояние сессии между паролем и вторым фактором? Какие роуты доступны в нём?
- Откуда второй шаг узнаёт, чью учётку подтверждает?
- Токен сброса: генератор, длина, срок, одноразовость, привязка к пользователю,
  повторная проверка при отправке нового пароля?
- Меняется ли id сессии при входе, смене пароля и роли? Гасится ли сессия на сервере
  при выходе и при сбросе пароля?

## Обходы, о которых забывают
- **Перечисление учёток по мелочам.** Тексты ошибок отличаются одним символом; код
  ответа разный; хеш пароля считается только для существующих — время выдаёт ответ.
  Блокировка учётки сама сообщает, что учётка есть.
- **Лимит, который считает не то.** Счётчик по IP обходится ротацией адресов; счётчик,
  сбрасываемый успешным входом, обнуляется входом в собственную учётку; лимит на
  HTTP-запросы не замечает несколько паролей в одном запросе (массив в JSON, батч).
- **Блокировка учётки** не мешает «распылению»: несколько популярных паролей против
  тысяч логинов. И сама даёт злоумышленнику способ заблокировать жертву.
- **Пропуск второго шага.** Если после пароля сессия уже «вошедшая», можно сразу
  открыть защищённые страницы, не вводя код.
- **Второй шаг не знает, кто прошёл первый.** Если логин для проверки кода приходит
  из cookie или поля формы, атакующий входит своим паролем и подставляет чужой логин,
  перебирая код.
- **Короткие коды без лимита.** 4–6 цифр перебираются, если лимит считается на
  сессию, а сессию можно просто начать заново.
- **Сброс пароля.** Токен не перепроверяется при финальной отправке формы; токен не
  привязан к учётке (можно сменить имя в скрытом поле); ссылка строится из
  подставленного заголовка `Host`/`X-Forwarded-Host`, и письмо жертвы ведёт на чужой
  сервер; токен утекает через `Referer` со страницы сброса.
- **Смена пароля** без требования текущего пароля или с логином из скрытого поля —
  вторая форма входа без защиты от перебора.
- **«Запомнить меня»** из предсказуемых частей подделывается, а угадывание такого
  cookie не попадает под лимит попыток входа.
- **Basic Auth** — пароль в каждом запросе, без лимита, без защиты от CSRF.

## Как исправить правильно
- Пароли: argon2id/bcrypt/scrypt; минимум 8 символов с MFA или 15 без неё; длина
  до 64+, любые символы; проверка по базам утёкших паролей; без принудительной смены.
- Единый ответ и сопоставимое время для всех ошибок входа, регистрации и сброса.
- Лимиты по учётке и по источнику, нарастающая задержка; CAPTCHA — только в дополнение.
- MFA: состояние «пароль принят, код не введён» хранится на сервере и не даёт доступа
  ни к чему, кроме формы кода; пользователь второго шага — из серверной сессии.
- Сброс: `secrets.token_urlsafe(32)`, хранить хеш, срок жизни, одноразовость, домен
  ссылки — из конфига, `Referrer-Policy: no-referrer`, после сброса — погасить все
  сессии, уведомить, не логинить автоматически.
- Повторная аутентификация перед сменой пароля, почты, привязки второго фактора.
- Сессии: ≥128 бит случайности, новый id после входа/смены прав, серверная
  инвалидация на выходе, idle- и абсолютный таймаут, cookie `Secure; HttpOnly;
  SameSite=Lax|Strict`, по возможности префикс `__Host-`.
- Если вход делегирован (Google и т. п.) — см. `oauth.md`; ограничение домена
  проверять на сервере по подтверждённой почте/`hd`.

## Ложные срабатывания
- `random` для не-секретных вещей (перемешивание, джиттер ретраев).
- `==` при сравнении не-секретов (имя роли, статус).
- Приложение без собственных паролей (только SSO) — смотреть тогда на сессию и OAuth.
- Сообщение «письмо отправлено, если адрес зарегистрирован» — это правильный вариант.
