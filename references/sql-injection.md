# SQL injection

## Суть
Приложение собирает текст SQL-запроса из строк, часть которых пришла извне, и база
исполняет «данные» как код. Итог — чтение чужих данных, обход входа, изменение и
удаление записей, а на некоторых СУБД — чтение файлов и выполнение команд на сервере.
Опасна любая часть запроса, куда попадает недоверенная строка, а не только `WHERE`.

## Где появляется в коде

**Python / asyncpg** — плейсхолдеры `$1, $2`:
```python
# плохо: f-строка, .format, %, + в тексте запроса
await conn.fetch(f"SELECT * FROM calls WHERE owner = '{email}'")
# хорошо
await conn.fetch("SELECT * FROM calls WHERE owner = $1", email)
```

**psycopg / psycopg2** — `%s` как плейсхолдер драйвера, а НЕ оператор `%`:
```python
cur.execute("SELECT * FROM t WHERE id = %s" % user_id)   # плохо: форматирование Python
cur.execute("SELECT * FROM t WHERE id = %s", (user_id,))  # хорошо: параметр драйвера
# имена таблиц/колонок — только через psycopg.sql:
from psycopg import sql
cur.execute(sql.SQL("SELECT * FROM {} ORDER BY {}").format(
    sql.Identifier(table), sql.Identifier(col)))          # и всё равно по белому списку
```

**SQLAlchemy** — опасны `text()` с f-строкой, `.order_by(text(...))`, `literal_column`,
`.filter("...")` со строкой, `session.execute(f"...")`:
```python
session.execute(text(f"... WHERE name = '{name}'"))              # плохо
session.execute(text("... WHERE name = :name"), {"name": name})  # хорошо
```

**Динамические части, которые нельзя параметризовать**: имя таблицы/колонки,
направление сортировки (`ASC/DESC`), `LIMIT/OFFSET` в некоторых драйверах, список
полей для `SELECT`, оператор сравнения. Параметр здесь не работает — только сверка с
заранее заданным словарём `{"date": "created_at", "title": "title"}`.

**Сборка `IN (...)`**: `",".join(ids)` в тексте — плохо; в PostgreSQL `= ANY($1)` с
массивом — хорошо. Для `LIKE` параметр тоже обязателен, а `%`/`_` во вводе экранируются
отдельно (это вопрос корректности, не инъекции).

**Node/JS**: шаблонные строки в `pg.query(`...${x}`)`, `sequelize.query` без
`replacements`, `knex.raw` с конкатенацией, `prisma.$queryRawUnsafe`. Хорошо —
`pg.query(text, [values])`, тегированный `prisma.$queryRaw\`...${x}\``.
**Прочее**: Java `Statement` вместо `PreparedStatement`, PHP `mysqli_query` с `.`,
Go `fmt.Sprintf` в `db.Query`.

## Как искать
```bash
rg -n 'f"[^"]*(SELECT|INSERT|UPDATE|DELETE|WHERE|ORDER BY)' --type py -i
rg -n "(execute|fetch|fetchrow|fetchval|executemany)\(\s*f['\"]" --type py
rg -n "(execute|fetch\w*)\([^)]*(\.format\(|%\s*[\(\w]|\+\s*\w)" --type py
rg -n "text\(\s*f['\"]|literal_column\(|order_by\(\s*text\(" --type py
rg -n "queryRawUnsafe|\.raw\(\s*`|query\(\s*`[^`]*\$\{" -g '*.{js,ts}'
```
Вопросы ревьюера:
- Есть ли хоть одно место, где текст запроса не является константой? Откуда в нём
  переменная — из запроса пользователя, из БД, из конфига, из ответа внешнего API?
- Как выбирается поле сортировки/фильтра из query-параметра? Есть ли белый список?
- Есть ли хранимые процедуры или функции PL/pgSQL с `EXECUTE` и конкатенацией внутри?
- Данные, уже лежащие в БД (имя пользователя, заголовок, текст расшифровки), потом
  попадают в другой запрос строкой?

Источники недоверенных данных: path/query/body, заголовки (`User-Agent`, `X-Forwarded-For`),
куки, имена загруженных файлов, содержимое из БД, вебхуки и ответы сторонних сервисов,
вывод LLM.

## Обходы, о которых забывают
- **Чёрный список слов** (`UNION`, `SELECT`, кавычки) не помогает: у СУБД много
  синтаксических вариантов — регистр, комментарии вместо пробелов, альтернативные функции,
  строковые литералы без кавычек (через коды символов или hex).
- **Самодельное экранирование кавычек** ломается на числовом контексте (кавычек
  нет вовсе), на обратном слэше перед кавычкой, на многобайтовых кодировках и на
  идентификаторах, где правила экранирования другие.
- **Вторичная (stored) инъекция**: при вставке значение передано параметром и лежит
  в БД «как есть», а позже другой код берёт его из таблицы и вклеивает в запрос, считая
  «своим». Доверие к данным из собственной БД — частая ошибка.
- **Слепые варианты**: даже если ответ не показывает результат и ошибки скрыты,
  атакующий различает «истину/ложь» по разнице в ответе, по условной ошибке, по
  задержке времени или по внешнему сетевому обращению самой СУБД. «Ничего не выводим —
  значит безопасно» — неверно.
- **Другие форматы ввода**: фильтр/WAF смотрит на query-строку, а значение пришло в
  JSON или XML, где кодирование символов (например, escape-последовательности) обходит
  проверку, а приложение потом декодирует его обратно.
- **Нестандартные места**: `ORDER BY`, имена колонок, `INSERT`/`UPDATE`-значения,
  `LIMIT` — там тоже бывает конкатенация, а тестируют обычно лишь `WHERE`.
- **ORM ≠ иммунитет**: «сырые» методы ORM и строковые фрагменты фильтров уязвимы так же.

## Как исправить правильно
1. Параметризованные запросы для всех значений — всегда, даже для «внутренних» данных.
2. Неизменяемый текст запроса; динамика — только выбором из заранее заданных фрагментов
   по белому списку (словарь «ключ от клиента → безопасный идентификатор»).
3. Типизированная валидация на входе (Pydantic: `int`, `UUID`, `Literal[...]`) — уменьшает
   поверхность, но не заменяет параметры.
4. Защита в глубину: роль БД с минимумом прав (без `SUPERUSER`, без `COPY ... PROGRAM`,
   без DDL у веб-роли), раздельные роли для чтения/записи, скрытые ошибки СУБД от
   пользователя, хранимые процедуры без динамического SQL.
5. Экранирование «вручную» — только как крайняя мера для унаследованного кода и только
   функциями драйвера, а не своими.

## Ложные срабатывания
- f-строка подставляет только константу из кода или значение из белого словаря
  (`ORDER_COLUMNS[key]`), а все пользовательские значения идут параметрами.
- `%s` внутри строки, переданной в `cur.execute(query, params)` вторым аргументом, —
  это плейсхолдер драйвера, а не форматирование.
- `psycopg.sql.SQL(...).format(sql.Identifier(...))` — безопасное цитирование
  идентификатора (но проверьте, что сам выбор таблицы разрешён пользователю).
- Миграции и скрипты с константным SQL без внешнего ввода.
- Сборка числа плейсхолдеров (`", ".join(f"${i}" for i in ...)`) — текст строится из
  счётчиков, значения идут параметрами.
