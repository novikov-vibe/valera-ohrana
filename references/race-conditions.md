# Состояния гонки (race conditions)

## Суть
Гонка возникает, когда несколько запросов обрабатываются одновременно и работают с
одними данными без надёжной синхронизации. Типичный случай — «проверил, потом
сделал» (TOCTOU): между проверкой и действием успевает пройти другой запрос.
Последствия — превышение лимитов (купон дважды, двойное списание, две задачи
вместо одной), обход 2FA и сброса пароля, повреждение данных.

## Где появляется в коде
- `SELECT` → проверка в Python → `INSERT/UPDATE` без транзакции, блокировки или
  уникального ограничения.
- Счётчики и балансы меняются как `x = row.x - 1; UPDATE ... SET x=$1`.
- «Одноразовый» токен/код помечается использованным отдельным запросом после проверки.
- Сессия/объект меняется в несколько шагов, и между шагами существует промежуточное
  состояние (пользователь уже залогинен, но 2FA ещё не требуется; запись создана,
  но поле с правами ещё пустое).
- Фоновая очередь: два воркера берут одну задачу.
- Токены, зависящие только от времени.
- ORM, скрывающая, где начинается и заканчивается транзакция.

```python
# плохо: два параллельных запроса оба пройдут проверку
row = await db.fetchrow("SELECT used FROM invites WHERE code=$1", code)
if row and not row["used"]:
    await grant(user)
    await db.execute("UPDATE invites SET used=true WHERE code=$1", code)

# хорошо: проверка и действие — одно атомарное условие
row = await db.fetchrow(
    "UPDATE invites SET used=true, used_by=$2 WHERE code=$1 AND NOT used RETURNING id",
    code, user.id)
if row is None: raise HTTPException(409)
await grant(user)          # лучше — в той же транзакции
```

```python
# баланс: условное обновление и проверка числа строк
res = await db.execute(
    "UPDATE accounts SET balance = balance - $1 WHERE id=$2 AND balance >= $1", amt, aid)
if res == "UPDATE 0": raise HTTPException(409)

# очередь: забрать задачу только одному воркеру
"SELECT id FROM jobs WHERE state='queued' ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1"

# «один на пользователя» — уникальный индекс, а не проверка в коде
"CREATE UNIQUE INDEX ON reviews(user_id, item_id)"   # + обработка UniqueViolationError
```

Node: те же SQL-приёмы; в Mongo — `findOneAndUpdate({_id, used:false}, {$set:{used:true}})`.

## Как искать
```
rg -n -U 'fetch(row|val)?\(.*SELECT[\s\S]{0,400}?execute\(.*(UPDATE|INSERT)' app/
rg -n 'used|redeemed|consumed|attempts|balance|quota|limit|count' app/ | rg 'UPDATE|SET'
rg -n 'FOR UPDATE|SKIP LOCKED|transaction\(\)|isolation' app/
rg -n 'UNIQUE|unique' migrations/
rg -n 'asyncio\.(gather|create_task)' app/
rg -n 'time\.time\(\)|datetime\.now\(\)' app/ | rg -i 'token|code|nonce'
```
Вопросы ревьюера:
- Где в этом обработчике проверка и где действие? Что произойдёт, если 20 одинаковых
  запросов придут в одну миллисекунду?
- Есть ли у инварианта («один раз», «не больше N», «не ниже нуля») опора в БД —
  уникальный индекс, CHECK, условие в `WHERE`?
- Какие промежуточные состояния видит другой запрос, пока этот выполняется
  (сессия, запись, статус)?
- Можно ли одновременно вызвать два разных эндпоинта, которые трогают один объект
  (оплата и добавление в корзину, подтверждение и правка)?
- Как воркеры делят задачи? Что если задача выполнится дважды — идемпотентна ли она?

## Обходы, о которых забывают
- **«Окно слишком маленькое».** Современные клиенты отправляют десятки запросов так,
  что они приходят практически одновременно (последний байт всех запросов разом);
  окно в миллисекунды достаточно. Нельзя полагаться на «маловероятно».
- **Скрытые многошаговые последовательности.** Один запрос внутри проходит несколько
  состояний — например, сначала создаёт сессию, затем проверяет, нужна ли 2FA. Если
  параллельный запрос попадает между ними — он видит «полностью вошедшего».
- **Гонки между разными эндпоинтами.** Проверка корзины при оплате и добавление
  товара — разные роуты; одна блокировка на роут не помогает.
- **Гонка на одном эндпоинте с разными данными.** Два запроса сброса пароля из одной
  сессии могут склеить пользователя одного запроса с токеном другого, если они
  пишутся в сессию отдельными шагами.
- **Частично созданный объект.** Запись вставлена, а ключ/права дописываются
  следующим запросом; в промежутке поле пустое (`NULL`, пустая строка), и проверка
  «совпадает ли токен с пустым» может пройти.
- **Токены из времени.** Два запроса в один момент получают одинаковое значение.
- **Блокировка сессии маскирует проблему.** Некоторые фреймворки обрабатывают
  запросы одной сессии по очереди; с разными сессиями гонка проявится.
- **Лимит в другом хранилище.** Счётчик попыток в сессии/кеше не защищает данные в БД.
- **Транзакция ≠ защита.** На уровне изоляции `READ COMMITTED` (по умолчанию в
  PostgreSQL) «SELECT, затем UPDATE» внутри транзакции всё равно гоняется.

## Как исправить правильно
- Сделать проверку и действие одной атомарной операцией: условный `UPDATE ... WHERE
  <условие> RETURNING` и проверка числа строк.
- Где нужна сложная логика — `SELECT ... FOR UPDATE` в транзакции или уровень
  `SERIALIZABLE` с повтором при конфликте.
- Инварианты закрепить в схеме: уникальные индексы (одна активная задача, один
  голос), CHECK (`balance >= 0`), внешние ключи — даже если код уже проверяет.
- Убрать промежуточные состояния у чувствительных операций: создавать объект
  целиком в одной транзакции; менять несколько полей сессии одной записью.
- Очереди — `FOR UPDATE SKIP LOCKED`, идемпотентные обработчики, ключи
  идемпотентности для внешних вызовов (привязанные к пользователю и параметрам).
- Внешний побочный эффект (письмо, платёж, задача в трекере) нельзя сделать атомарным
  с локальной транзакцией: фиксировать намерение в БД, выполнять из воркера,
  сверять неизвестные исходы перед повтором.
- Токены — только из CSPRNG.
- Тест: N параллельных запросов (`asyncio.gather`) против инварианта.

## Ложные срабатывания
- `SELECT` + `UPDATE`, защищённые уникальным индексом или `FOR UPDATE` в той же транзакции.
- Операции, которые идемпотентны по смыслу (повторная установка того же значения).
- Чтение для отображения без последующего действия.
