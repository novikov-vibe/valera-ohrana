# Контроль доступа и IDOR

## Суть
Контроль доступа решает, может ли уже опознанный пользователь выполнить конкретное
действие над конкретным объектом. Ошибки бывают трёх видов: вертикальные (обычный
пользователь достаёт админскую функцию), горизонтальные (чужие объекты того же типа —
классический IDOR) и контекстные (действие разрешено не в том состоянии процесса).
Последствия — утечка и порча чужих данных, захват админских прав.

## Где появляется в коде
- Роут берёт `id` из пути и грузит запись по первичному ключу, не сверяя владельца.
- Проверка «залогинен ли» (`Depends(current_user)`) есть, а проверки «можно ли ему
  этот объект» нет — аутентификация подменяет авторизацию.
- Роль/признак админа читается из тела запроса, cookie, скрытого поля, query-параметра.
- Отдача файлов (`FileResponse`, `StaticFiles`) по имени из URL без проверки прав.
- Списки фильтруют по видимости, а детальная страница, экспорт, аудио, вложения — нет.
- Админские роуты защищены только тем, что ссылки на них нет в меню.

```python
# плохо: любой вошедший читает любой созвон
@router.get("/calls/{call_id}")
async def get_call(call_id: int, user=Depends(current_user)):
    return await db.fetchrow("SELECT * FROM calls WHERE id=$1", call_id)

# хорошо: одна функция доступа, предикат видимости в самом запросе, 404 вместо 403
async def load_call_for(user, call_id: int):
    row = await db.fetchrow(
        "SELECT c.* FROM calls c WHERE c.id=$1 AND " + VISIBLE_SQL, call_id, user.id)
    if row is None:
        raise HTTPException(404)
    return row
```

```python
# плохо: роль из запроса
if body.get("is_admin"): ...
# хорошо: роль только с сервера
if user.role != "admin": raise HTTPException(404)
```

Node/Express: `app.get('/api/orders/:id', auth, (req,res)=>Order.findById(req.params.id))` —
то же самое; правильно `Order.findOne({_id: id, ownerId: req.user.id})`.

## Как искать
```
rg -n '@(router|app)\.(get|post|put|patch|delete)\(.*\{[a-z_]*id\}' app/
rg -n 'WHERE\s+id\s*=\s*\$1' app/                  # выборка по id без владельца
rg -n 'FileResponse|StaticFiles|send_file|sendFile' app/
rg -n 'is_admin|role|permission' app/ | rg -n 'body|form|query|cookie|request\.'
rg -n 'X-Original-URL|X-Rewrite-URL|X-Forwarded-|Referer' app/
rg -n 'findById|findByPk|get_or_404|\.get\(.*id' src/
```
Вопросы ревьюера:
- Перечислите все роуты, принимающие идентификатор объекта. Для каждого: где проверка,
  что текущий пользователь имеет право именно на этот объект и именно на это действие?
- Одна ли функция проверяет доступ, или в каждом роуте своя копия логики?
- Изменяющие запросы (PUT/DELETE/экспорт/массовые операции) проверяются так же, как чтение?
- Есть ли роуты без `Depends(current_user)` — и задуманы ли они публичными?
- Совпадает ли ответ для «нет такого» и «нет прав» (иначе — перечисление объектов)?

## Обходы, о которых забывают
- **Проверка только в интерфейсе.** Кнопка скрыта — но эндпоинт отвечает любому, кто
  пришлёт запрос руками. Сервер обязан проверять сам.
- **Секретный URL вместо проверки.** Адрес админки «никто не знает», но он попадает в
  JS-бандл, `robots.txt`, историю, логи прокси. Неизвестность — не защита.
- **Непредсказуемые id (UUID) как защита.** Они затрудняют перебор, но утекают через
  другие ответы API, ссылки, письма, вложения. Проверка права всё равно нужна.
- **Правило на фронт-прокси по пути и методу.** Если nginx/шлюз закрывает `POST /admin`,
  а приложение принимает тот же путь через другой метод, другой регистр, лишний слэш,
  суффикс `.json` или служебный заголовок переопределения пути — правило не совпадает,
  а приложение действие выполняет. Проверка должна жить в приложении, после
  маршрутизации.
- **Подмена метода.** Проверка навешана на `POST`, а `GET` с теми же параметрами (или
  `_method=`-оверрайд) тоже меняет данные.
- **Многошаговые процессы.** Права проверяются на первом шаге («открыть форму»), а
  финальный шаг («подтвердить») принимается от кого угодно — злоумышленник шлёт сразу его.
- **Доверие к `Referer`/заголовкам.** «Пришёл со страницы админки — значит админ»:
  заголовок полностью контролирует клиент.
- **Утечка в редиректе.** Роут отвечает 302 на страницу входа, но в теле ответа уже
  отрендерены чужие данные.
- **Горизонталь → вертикаль.** Через IDOR на профиле читается/меняется учётка админа
  (почта, токен сброса), дальше — полные права.
- **Прямые ссылки на файлы.** Записи, расшифровки, выгрузки лежат под предсказуемыми
  именами в публичной папке или бакете.
- **Гео/IP-ограничения** обходятся прокси и подменой клиентских данных о местоположении.

## Как исправить правильно
- Запрет по умолчанию: роут без явного правила доступа не должен существовать
  (зависимость на уровне `APIRouter(dependencies=[...])`, тест, перечисляющий роуты).
- Одна функция «загрузить объект для пользователя» с предикатом видимости внутри SQL;
  ею пользуются все роуты, включая аудио, экспорт, вложения. Ответ — 404.
- Список и детальная страница используют один и тот же предикат видимости.
- Роль и идентичность — только из серверной сессии, никогда из тела/cookie без подписи.
- Проверка действия, а не только чтения: «может видеть» ≠ «может редактировать».
- Файлы — вне публичной папки, отдаются через роут с той же проверкой.
- Защита в глубину: непредсказуемые идентификаторы, Row-Level Security в PostgreSQL
  для критичных таблиц, журнал отказов в доступе.
- Тесты на двух пользователях: объект A недоступен B на чтение, изменение, удаление,
  экспорт. Тест, что каждый роут требует вход (кроме явного списка исключений).

## Ложные срабатывания
- Публичные по замыслу ресурсы (лендинг, health-check, вебхук с проверкой подписи).
- Выборка по id внутри фоновой задачи, где id взят из БД, а не от пользователя.
- Запрос по id, после которого стоит явная проверка владельца/членства (проследить!).
- Админские роуты за отдельной зависимостью `require_admin`, навешанной на роутер.
