# Ревью безопасности веб-приложения

Задача — найти в **своём** коде реальные уязвимости и предложить правильные
исправления. Справочники в `references/` написаны по мотивам PortSwigger Web
Security Academy (своими словами, со ссылками) и OWASP Cheat Sheet Series.

Хорошее ревью безопасности отличается от плохого не длиной списка, а тем, что
каждая находка — это конкретный путь: *кто* (какой пользователь или внешний
источник) *что отправляет*, *через какой код* это проходит и *что ломается*.
Находка без такого пути — догадка; её либо доказать по коду, либо отбросить.

## Порядок работы

### 1. Определи объём и убедись, что код актуальный
- Проверь, что смотришь свежий код: `git status`, `git log -1`, отставание от
  `origin/<основная ветка>`. Если рабочая копия отстала или нужный код лежит в
  невлитой ветке/другом worktree — выбери, что ревьюить, и назови ветку и
  коммит в начале отчёта. Ревью устаревшего кода вводит в заблуждение.
- Diff/PR/ветка → смотри изменённые файлы, но прослеживай данные и за пределы
  diff (вызывающий код, общие хелперы, миграции).
- Весь проект → начни с точек входа.

### 2. Прочитай правила проекта
Найди `CLAUDE.md`, `docs/DECISIONS.md`, `SECURITY.md` и подобное. В проекте
часто уже есть правила безопасности («доступ проверяется в одном месте»,
«изменяющие запросы проверяют Origin», «ключи только из env»). Нарушение
собственного правила проекта — сильная находка, даже если общий справочник
о таком не говорит. И наоборот: не предлагай переделывать принятое решение,
если оно безопасно.

### 3. Составь карту поверхности атаки
Перечисли коротко (для себя, не обязательно в отчёт):
- **Точки входа**: HTTP-роуты, вебхуки и callback'и, обработчики сообщений
  из чатов, фоновые задачи с данными извне, расширения браузера, CLI.
- **Кто может прийти**: аноним, вошедший пользователь, пользователь другой
  команды, админ, внешний сервис, автор текста, который потом прочитает LLM.
- **Недоверенные данные**: параметры, тело, заголовки (Host, Origin,
  X-Forwarded-*), имена и содержимое файлов, URL для скачивания, тексты из
  чатов/писем/расшифровок, ответы внешних API.
- **Ценное**: чужие записи, токены и ключи, отправка сообщений от имени
  пользователя, создание задач во внешних системах, деньги/квоты.

### 4. Выбери темы и прочитай справочники
Не читай всё подряд — выбери по признакам в коде:

|---|---|

| MongoDB/Redis/JSON-запросы из тела | `nosql-injection.md` |
| `subprocess`, `os.system`, `shell=True`, ffmpeg/конвертеры | `os-command-injection.md` |
| Шаблон собирается из строки пользователя, `Template(...)`, `render_template_string` | `ssti.md` |
| Разбор XML, SVG, DOCX/XLSX | `xxe.md` |

| `pickle`, `yaml.load`, `marshal`, десериализация из cookie/очереди | `deserialization.md` |

| Платные внешние API (LLM, распознавание речи, SMS) запускаются по действию пользователя | `business-logic.md` (повторный запуск, лимиты), `race-conditions.md` (двойной запуск) |

**Сколько читать.** Сначала разделы «Обходы, о которых забывают» и «Ложные
срабатывания» — их хватает, чтобы отсеять кандидатов. Справочник целиком
читай, когда в коде нашёлся реальный кандидат по этой теме.

Если признаков темы нет — не проверяй её глубоко и не расписывай. В отчёте
хватит одной строки «проверено, признаков нет: …», чтобы был виден охват.

### 5. Проверь каждую подозрительную точку
Для каждого кандидата пройди путь данных от входа до опасного действия:
1. Откуда приходит значение и кто им управляет?
2. Какие проверки стоят по дороге? Работают ли они против обходов из раздела
   «Обходы, о которых забывают» соответствующего справочника?
3. Что конкретно получит атакующий?

Если путь не складывается (данные не доверенные только в теории, проверка
стоит раньше, роут недоступен извне) — отбрось или пометь как «укрепление»,
а не уязвимость. Сверься с разделом «Ложные срабатывания».

Тесты проекта — хороший способ подтвердить находку: если можешь написать
короткий тест, который показывает проблему, это лучшее доказательство.
Если менять проект нельзя (ревью «только чтение»), скопируй код во временную
папку (`git worktree add` или `git archive | tar -x`) и пиши тест там; путь к
тесту укажи в отчёте. Не атакуй живые чужие системы и прод — только локальный
код и тесты.

### 6. Отчёт

Пиши для двух читателей: разработчику — где и что исправить, заказчику —
человеческим языком, чем это грозит. Если в проекте принято писать отчёты
без путей и имён функций (см. `CLAUDE.md`), вынеси технические детали в
отдельный блок под каждой находкой.

Шаблон:

```
## Итог
Одна-две фразы: сколько серьёзных проблем, главное.

## Находки
### 1. <Короткое название> — <Критично | Высоко | Средне | Низко>
**Что может случиться:** кто и что сможет сделать, простыми словами.
**Как это происходит:** путь данных от входа до проблемы.
**Как исправить:** конкретное изменение (и почему наивный вариант не подойдёт).
**Где:** файл:строка.
**Тема:** ссылка на справочник / страницу Академии.

## Укрепления (не уязвимости)
Коротко, по строке: что стоит добавить для защиты в глубину.
```

Серьёзность:
- **Критично** — без входа или любым пользователем: чужие данные массово,
  выполнение кода, захват аккаунта, ключи.
- **Высоко** — вошедший пользователь получает чужие данные/действия, или
  атака требует одного клика жертвы.
- **Средне** — нужны особые условия или ущерб ограничен.
- **Низко** — раскрытие мелочей, слабая защита в глубину.

Свои сотрудники тоже атакующие: если человек с законным доступом может выйти
за пределы своих прав (удалить чужое, выдать себе роль, многократно
запустить платную обработку), оценивай по ущербу — обычно Высоко или Средне,
а не Низко на том основании, что «это же свои».

Сортируй находки по серьёзности. В конце — строка «Проверено, признаков нет:
…». Если ничего не нашлось — так и скажи.

## Исправление
Если просят исправить — чини по разделу «Как исправить правильно»
справочника, а не точечной заплаткой против конкретной строки. Добавляй тест,
который падал бы без исправления. Правила проекта (миграции, где живёт
проверка доступа и т. п.) соблюдай как в любой другой правке.
